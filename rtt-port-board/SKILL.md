# rtt-port-board

Ports a new CVITEK CV18xx board through the **complete** verified pipeline.
Repos involved:

- **rt-thread master** (`~/Public/rtt_master/rt-thread-master`) — the platform
  layer lives here: `bsp/cvitek/{drivers,libraries,chips,boards,tools}` and the
  Milk-V BSP projects. Board code is shared **per core**, not per board.
- **cvi_rtt** (`.../rt-thread-master/cvi_rtt`) — solution / product layer only:
  `solutions/<sol>/customization/<proj>/` (project config), `boards/bootimgs/`
  (prebuilt boot images), packaging.

Also needs the **boot firmware tree** `~/Public/rtt_boot_firmware` for
boot0/fip.bin (via the `rtt-build-boot-firmware` skill).

> Legacy tree `~/Public/rtt_master/rt-thread` (branch `cv18xx-dev`) still has
> per-board dirs `cvi_rtt/boards/<SOC_TYPE>/`. Do not follow that layout on
> master; it is only relevant when working in the dev tree.

## Inputs to collect first (ask the user if unknown)

| input | example | determines |
|---|---|---|
| board name | `cv1813h_wevb_0007a_spinor` | boot firmware defconfig, project name |
| chip / SOC_TYPE | `cv181xh_bga` | `SOC_TYPE_*`, model-table entry, DDR size |
| core | A53 / C906 | which `bsp/cvitek/boards/<core>/` is used |
| chip family | cv181x (vs cv180x) | pinctrl dir, `__CV18xX__` |
| boot media | spinor / spinand / emmc | `<arch>_<media>` bootimgs dir |
| DDR size (MB) | 256 | `CVI_BOARD_DDR_SIZE_MB` in the project `.config` |
| hub USB port / UART node | 3 / `/dev/ttyUSB0` | flash & verify — always from the prompt |

## Step 1 — platform layer: the model table (usually no code change)

1. **Chip model** `bsp/cvitek/chips/Kconfig.chips` — only for a genuinely new
   model. A `config SOC_CV18xx` with `select SOC_SERIES_*`, `select SOC_PKG_*`
   and (for external DDR) `select SOC_DDR_EXTERNAL`; the DDR size of a package
   part goes in the `SOC_DDR_SIZE_MB` defaults right below.
2. **Board code** `bsp/cvitek/boards/<core>/` — `aarch64_a53`, `aarch32_a53`,
   `riscv_c906m`. Every board on the same core reuses this one directory; only
   a **new core** adds one (plus its `SConscript`/`Kconfig` and the
   `ARCH_TARGET` branch in `cvi_rtt/SConstruct`).
3. **Never hardcode board parameters there.** DDR size, heap bounds, flash
   layout come from the project `.config`. `aarch64_a53/board.c` builds
   `platform_mem_desc` from `DDR_START`/`DDR_END` (board.h, derived from
   `CVI_BOARD_DDR_SIZE_MB`); a 512MB board needs no edit in `board/`.

The flash layout is load-bearing (do NOT "align" it): bl2 reads BOOT@0xc000
(128KB) and mini-boot reads PRIM@0x2c000 — offsets are hardcoded in boot
firmware. The partition table stays in
`solutions/<sol>/customization/<proj>/partition_<layout>.xml`.

## Step 2 — cvi_rtt: register the SOC_TYPE and the project

1. **`cvi_rtt/boards/Kconfig.chips`** — add `config SOC_TYPE_<X>` to
   `choice CHIP_SERIES` with `select SOC_SERIES_*` / `select SOC_PKG_*`
   (and `select CVITEK_CORE_*` for a new core). This is the封装-level symbol
   cvi_rtt uses everywhere.
2. **`cvi_rtt/boards/chip_list.json`** — list the `SOC_TYPE` under its series;
   `rtconfig.py` reads it to derive `boards/bootimgs/<series>/`.
3. **`cvi_rtt/rtconfig.py`** — `SOC_MACRO_MAP`: `"<soc>": "SOC_TYPE_<X>"`.
4. **Project dir** `cvi_rtt/solutions/<sol>/customization/<proj>/` — clone the
   same-family project's `*.c` + **`.config` (the only configuration source;
   `PROJECT=<proj>` copies it to the solution root and generates
   `rtconfig.h` from it — never commit an `rtconfig.h` in the project)** +
   `partition_<layout>.xml`. Set in `.config`:
   ```
   CONFIG_SOC_TYPE_<X>=y
   CONFIG_PROJECT_<PROJ>=y
   CONFIG_CVI_BOARD_DDR_SIZE_MB=<real DDR size of this board>
   ```
   `CONFIG_PROJECT_*` is generated by `tools/gen_project_kconfig.py` from the
   directory name — creating the directory registers the project.

## Step 3 — boot firmware (the part that eats days if done wrong)

Three images, three sources — see the `rtt-build-boot-firmware` skill for the
driver. Summary:

| image | flash slot | built by |
|---|---|---|
| boot0 (FSBL, DDR init + USB DL) | @0x0 | `rtt_boot_firmware`: board defconfig + `ENABLE_BOOT0=y` → `driver.sh boot0` |
| boot (mini-boot, jumps to rtt.bin) | @0xc000 | **cvi_rtt**: `make cv18xx_boot PROJECT=<arch/media project>` |
| fip.bin (USB-flashing session only) | — (RAM) | `rtt_boot_firmware`: board defconfig + RTT flavor → `driver.sh fip` |

Deploy: all three into `cvi_rtt/boards/bootimgs/<series>/<arch>_<media>/`
(`<arch>` = riscv / arm / arm32). They are copied into `image/` at packaging
time; there is no `tools/fip/` tree any more.

**Hard requirements (each one silently bricks flashing otherwise):**
- The board's SDK defconfig (`build/boards/cv181x/<board>/<board>_defconfig`)
  must contain `CONFIG_USE_4K_ERASE_SIZE_FOR_JFFS2=y`, else u-boot erases in
  64KB blocks, the 48KB/128KB partitions don't divide, and EVERY flash write
  silently fails while usb_dl reports success. (cv1812h was missing it.)
- fip must be RTT flavor (`ENABLE_RTT_UPDATE=y`, `ENABLE_FREERTOS=n`, no
  "CVIRTOS Build" string). driver.sh checks both; for **spinand** build it by
  hand (`setconfig`), the driver's 4K-erase check is a false positive there.
- **Never reuse another board's boot0/fip** — DDR params are board-bound
  (cross-flash ⇒ `E:PARAM1 magic` boot loop or usb_dl stalls in stage 1).
  The mini-boot is per-core, so the same `boot` is shared by all boards of one
  core+media.
- `make` never rebuilds `boot0` or `fip.bin`: `make smart_doorbell` only
  builds `rtt.bin` and packs the prebuilt boot images from `bootimgs/`.

## Step 4 — build

```bash
cd cvi_rtt
make smart_doorbell PROJECT=<proj>     # -> install/smart_doorbell_<proj>/image/
```

`install/<solution>_<project>/` is the only output dir (there is no shared
`generated/`; `install/` is gitignored). If it errors with a symlink
`FileExistsError` after renaming/switching projects:
`rm -f solutions/<sol>/{rtconfig.h,.config}` and re-run.

## Step 5 — flash & verify (the ONLY trustworthy success criteria)

```bash
RESET_SERIAL=0 bash ~/.claude/skills/rtt-flash/flash-rtt.sh -p <hub_port> \
    -i .../cvi_rtt/install/smart_doorbell_<proj>/image/
```

`-P`/`--project` is not supported by the installed script — always pass `-i`.

Capture UART (115200) across a power cycle and check, in order:

1. `FSBL ...:<new build timestamp>` — boot0 actually written (stays old = the
   4K-erase/flavor trap above).
2. `DDR ... BIST PASS` with the right DDR type (board-matched boot0).
3. `image_buf:0x594b53430001a805` — BOOT partition head = mini-boot magic
   (`05a80100`+"CSKY"); `0x...732540f1` = stale cvirtos (wrong image).
4. RISC-V: `j 0x80050000`; AArch64: `Switch to EL2-NS` then `j 0x80200000`;
   AArch32: `Switch to AArch32 SVC-NS` then `j 0x80200000`.
5. RT-Thread banner → `version` build time = today → `msh />`, `free` sane.

usb_dl's "USB download complete / FLASH SUCCESS" alone proves **nothing** —
always confirm via the boot log.
